# Database schema

PostgreSQL 16. The schema is created by Alembic migration `0001_create_boards_and_tasks.py`.

## `boards`

| Column | PostgreSQL type | Constraints |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Primary key, not null |
| `name` | `VARCHAR(150)` | Not null; trimmed value must contain at least one character |
| `created_at` | `TIMESTAMPTZ` | Not null; defaults to `CURRENT_TIMESTAMP` |

Check constraint:

- `ck_boards_name_not_blank`: `char_length(trim(name)) > 0`

Board names are deliberately not unique. The brief does not require uniqueness, and a team may reuse a project name in another period.

## `tasks`

| Column | PostgreSQL type | Constraints |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Primary key, not null |
| `board_id` | `BIGINT` | Not null; foreign key to `boards.id` |
| `title` | `VARCHAR(200)` | Not null; trimmed value must contain at least one character |
| `description` | `TEXT` | Nullable |
| `status` | `VARCHAR(20)` | Not null; defaults to `TODO`; limited to three values |
| `created_at` | `TIMESTAMPTZ` | Not null; defaults to `CURRENT_TIMESTAMP` |
| `updated_at` | `TIMESTAMPTZ` | Not null; defaults to `CURRENT_TIMESTAMP` |

Constraints:

- `tasks.board_id -> boards.id ON DELETE CASCADE`
- `ck_tasks_title_not_blank`: `char_length(trim(title)) > 0`
- `ck_tasks_status_valid`: `status IN ('TODO', 'IN_PROGRESS', 'DONE')`

The foreign key prevents direct SQL inserts from referencing a board that does not exist. `ON DELETE CASCADE` makes deletion deliberate and database-enforced: deleting a board removes all tasks that cannot exist meaningfully without it.

## Indexes

| Index | Columns | Reason |
|---|---|---|
| `boards_pkey` | `id` | Created by the primary key for direct board lookup |
| `tasks_pkey` | `id` | Created by the primary key for direct task lookup/update/delete |
| `ix_tasks_board_status` | `board_id, status` | Supports listing all tasks in one board and the same query filtered by status |

No index was added for `created_at`. The brief assumes a manageable dataset and does not require time-range searches, so another write-time cost is not justified.

## Considered and rejected

A separate status lookup table was considered but rejected. The set contains exactly three stable values defined by the product brief, so a check constraint provides direct database integrity without an extra join or lifecycle for configurable status rows.

Soft deletion was also considered but rejected. There is no audit or recovery requirement, and implementing it would complicate every list query and foreign-key deletion rule without solving a requested use case.
